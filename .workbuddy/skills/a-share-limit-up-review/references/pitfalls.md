# 口径坑与工程踩坑

## 口径类（会导致结论错误，必读）

### 1. 同花顺 `currency_value` / `order_amount` 不是成交额 ⚠️ 最致命

实测某股 `currency_value` = 58.16 亿，但按「换手率 4.357% × 流通市值」反推只有约 5.8 亿，**差 10 倍**。
用它汇总会得出「涨停股合计成交 1.03 万亿 > 两市总成交 1.84 万亿」的荒谬结论。

→ 成交额、换手率、市值、封单**一律取东财字段**（`amount` / `hs` / `ltsz` / `fund`）。
→ 收尾自检：`涨停股合计成交额 ÷ 两市成交额` 应落在 **3%~8%**。
   注意该比值**与涨停家数强相关**，家数腰斩时会自然跌破 3%（实测 2026-09-17 仅 47 家 → 2.0%，
   而前一日 89 家 → 4.3%）。此时应改用**单只中位成交额**做交叉验证
   （同日中位 5.53 亿 vs 前日 3.88 亿，不降反升 → 字段源无误），并在报告口径说明中写明原因。

### 2. 家数不要数池子条数

- 跌停/炸板家数用 `limit_up_count` / `limit_down_count` 的**汇总字段**。
  实测 2026-09-16 跌停 4 家，而 `limit_down_pool` 返回 0 条。
- 涨停家数用 `len(info)` 与 `limit_up_count.today.num` 互相验证。

### 3. 排序 tie-break 必须完整，否则结果不可复现

`collections.Counter` + `set()` 排序时，同分项的先后取决于 `set()` 迭代顺序，
而 **Python 对 str 的哈希每进程随机化** → 同一份数据两次跑出的「行业 Top18」不一样。

```python
# 错：同分项顺序随机
sorted(set(hy0) | set(hy1), key=lambda k: -(hy0.get(k, 0) * 2 + hy1.get(k, 0)))
# 对：补全 tie-break
sorted(set(hy0) | set(hy1),
       key=lambda k: (-(hy0.get(k, 0) * 2 + hy1.get(k, 0)), -hy0.get(k, 0), -hy1.get(k, 0), k))
```

### 4. 涨跌幅字段的可靠源

- 腾讯 `qt.gtimg.cn` 的 f32 可靠。
- 东财 `push2delay` 的 clist `f24`/`f25` **不可靠**（实测「元件」60 日显示 -6.5%，实际 +41.8%），**不可用于排序**。

### 5. 「晋级率」的分组口径

昨日涨停股按**昨日连板数**分组（首板 / 连板），不要按今日连板数分组——
后者是本轮的结果而非前提，会让「首板晋级率」失真。

### 6. `x or 默认值` 会把「0」当成缺失值 ⚠️

报告模板里若用 `sorted(perf, key=lambda x: -(x["pct"] or -99))` 排序，
则 **涨跌幅恰为 0.00% 的个股（当日收平）会被当成缺失值排到最末尾**，
「最弱」标签就会指向一只平盘股而不是真正的最弱股。

实测 2026-09-17：`PERF_MIN` 取 `min(pcts)` 得 -8.09%（远望谷），
而同一次运行的 `PERF_MIN_NAME` 却是「浙江永强」（pct=0.0）——两个数字自相矛盾。
改用显式 None 判断：

```python
perf_sorted = sorted(perf, key=lambda x: -(x["pct"] if x["pct"] is not None else -999))
```

**通用规则**：凡是给数值字段设默认值，一律用 `if v is None` 而不是 `v or d`；
收尾时加一条自检 —— 「最弱股的名称与其涨跌幅是否对应同一个代码」。

### 7. 东财 `fbt` 是 HHMMSS 整数，切字符串前必须 `zfill(6)` ⚠️

炸板池（`em_ZB.pool`）里 `fbt` 是不带前导零的**整数**（`92500` = 09:25:00，`130052` = 13:00:52）。
若按 `str(int(v))[:2] + ":" + str(int(v))[2:4]` 格式化，
**10:00 之前的封板时间全部被切错**：`92500` → `92:50`、`95842` → `95:84`、`94045` → `94:04`。
因为 09:00 段的 HH 只有 1 位，`[:2]` 把 `H H` 的后一位和分针的第一位一起吃掉了。
`10:00` 之后恰好有 6 位，所以 bug 只在早盘时段显形，极易漏检。

```python
def hhmm(v):
    s = str(int(v)).zfill(6)      # 92500 -> '092500'
    return s[:2] + ":" + s[2:4]   # -> '09:25'
```

> 注意与 `r0`（涨停池，来自同花顺）区分：那里的 `fbt` 已经是 `"09:30:09"` 字符串，直接 `[:5]` 即可。
> 两个源的字段同名不同型，写模板时不要混用同一段格式化代码。

**自检**：报告出图后 `grep -o "[0-9][0-9]:[0-9][0-9]"` 取唯一值，
**不允许出现 `9x:xx`（90~99 点）或 `1x:xx` 中分钟 >59 的值**。

### 8. 东财涨停池与同花顺家数的差额，必须能全部归因到北交所

东财 `em_ZT.tc` 会比同花顺 `num` 多出 `920xxx` 的北交所标的：

| 日期 | 同花顺 | 东财 tc | 差额 | 归因 |
|---|---|---|---|---|
| 2026-09-18 | 77 | 78 | 1 | 920298 |
| 2026-09-21 | 101 | 103 | 2 | 920478 峆一药业、920427 华维设计 |

**处理规范**：报告统一按**沪深口径**（同花顺数）出数，并在「数据口径」里写明
「东财池 N 条，差额 M 只为北交所标的（列出代码），已剔除」。

**自检**：每次复盘都跑一次 `set(em_codes) - set(ths_codes)`，
若差额里出现沪深代码（`60/00/30/68` 开头）→ 说明字段错位或某一源漏数，必须排查，不要直接采用同花顺口径掩盖。

```python
r = B["dates"][D0]
diff = sorted({x["c"] for x in r["em_ZT"]["pool"]} - {x["code"] for x in r["ths_zt"]["info"]})
assert all(c.startswith("92") for c in diff), f"非北交所差额: {diff}"
```

#### 8b. 差额里出现**沪深代码**（2026-10-26 首次捕获：301502 华阳智能）⚠️

10-26 的 `em_ZT.pool` 55 只、同花顺 54 只，差额 `['301502']` —— **深市创业板，不是北交所**。
说明上式 `assert` 会直接打断（这是好事，不要为了跑通把 assert 删掉或放宽成只打个 warning）。

**实际成因是「同花顺未收录该只」，不是字段错位 —— 与第 16 条互为镜像**（16 是两源都不收、只进东财炸板池；
这里东财收了、同花顺不收）。301502 华阳智能当日 +20.00%、3 板，但**收盘时封单仅 0.01 亿**（成交 6.23 亿、换手 34.9%），
与 09-22 瑞芯微 / 09-24 三羊马同型。判定步骤：

1. 用腾讯快照核对该股确实涨停（`pct` 与涨停价对齐）→ 排除东财多算。
2. 看**封单**：`fund` 极小（<0.05 亿）且换手很高 → 属"收在涨停价但封不住"的边缘形态，两源收录规则不同。
3. 确认"东财对、同花顺没收"后，按 SKILL 的口径规范处理：
   **家数仍取同花顺（54）**，在「数据口径」里单列披露「东财池 55 只，差额 1 只 301502 华阳智能（深市，同花顺未收录）」，
   并补一句**敏感性说明**（若按东财口径：涨停 55 家、3 板 6 只、晋级 15 只 / 18.8%）——证明结论方向不变。

**不要做的两件事**：① 直接把家数改成 55（与历史基线全部不可比）；② 把 assert 降级（此处正是它该报错的地方）。
可复用结论：**差额必须先分类（北交所 / 漏收录 / 真错位），分类前不得采用任何一方的家数**。

### 9. 同花顺「跌停池」明细接口会 404，不能用它判断跌停家数

`dataapi/limit_up/limit_down_pool` 实测返回 **HTTP 404**（2026-09-21），`ths_dt` 落盘为 `None`；
东财侧 `em_DT` 会出现 `tc=2` 但 `pool=[]` 的自相矛盾状态。

**唯一可靠源是汇总字段** `ths_zt["limit_down_count"]["today"]["num"]`（与第 2 条同源）。

**处理规范**：明细拿不到时，报告写「跌停 N 家（同花顺汇总口径；明细池接口当日不可用，未列名单）」，
**不要**因为池子返回 0 条就写成「跌停 0 家」——这正是第 2 条踩过的坑。

### 10. 同花顺封单字段（`order_amount`）收盘 30 分钟内仍在刷新 ⚠️

**同一交易日的两次抓取，同花顺 `order_amount` / `order_volume` 会变**：

| 个股 | 15:31 抓取 | 16:11 抓取 | 倍数 |
|---|---|---|---|
| 我爱我家 000560 | 327 万 | 5,916 万 | 18× |
| 百通能源 001376 | 220 万 | 11,980 万 | 54× |
| 华森制药 002907 | 106 万 | 3,550 万 | 33× |
| 奥赛康 002755 | 13.3 万 | 271 万 | 20× |

同一时段内**家数、涨跌幅、封板时间、成交额都没变**，只有封单字段在变 →
说明同花顺封单是**延迟结算字段**，15:30 抓到的不是终值。

**处理规范**：
1. 封单口径**一律取东财 `fund`**（本流程已如此），不受此影响；
2. 若将来改用同花顺 `order_amount` 出「封单结构性结论」，
   **必须等 16:00 之后再抓**，否则会把「某只票封单只有几百万」当成事实写进报告；
3. 盘中/早于 16:00 的补跑，报告中「封单合计」类数字应标注时点。

**幂等自检（判断数据是否已稳定，可复用）**：

```python
def canon(o):                       # 排序归一化：列表按 code/c 排序后再比
    if isinstance(o, dict): return {k: canon(v) for k, v in sorted(o.items())}
    if isinstance(o, list):
        if o and isinstance(o[0], dict):
            key = "code" if "code" in o[0] else ("c" if "c" in o[0] else None)
            if key: return sorted((canon(x) for x in o), key=lambda x: str(x.get(key)))
        return [canon(x) for x in o]
    return o
# 两次抓取后：json.dumps(canon(a), sort_keys=True) == json.dumps(canon(b), sort_keys=True)
```

> **必须归一化后再比**：同一份数据两次抓取的**列表顺序本身不稳定**
> （`em_ZB` / `ths_block` 的首项会互换），直接 diff 会看到几十处「差异」，
> 全是排序抖动，容易误判成数据变化。

### 11. 指数日线（`index_hist`）盘后会把「当日行」移出返回窗口 ⚠️

**现象**：同一交易日盘后多次抓取，`index_hist[code].rows` 的**最后一行会变**。
2026-09-21 实测（`zs_1B0688` 科创50）：

| 抓取时刻 | rows 末两行 |
|---|---|
| 16:11 | … `20260918`, **`20260921`** ← 含当日 |
| 16:34 / 16:36 | … `20260917`, `20260918` ← **当日消失** |

16:11 之后当日行被移出窗口、稳定为「不含当日」，与代码无关，是接口侧行为。

**为什么不会污染报告**：本流程的当日成交额取自**实时快照** `indexes[sym].amount_wan`，
历史行只按**显式日期**查 D1/D2（`hist_row(hcode, D1)`），所以 `rows` 里有没有当日都无影响。

**必须遵守的两条**：
1. **禁止用 `index_hist[code]["rows"][-1]` 当作「当日」** —— 它在 16:30 后会静默回退到前一交易日，
   算出来的「今日成交额」会等于昨日值，且不报错。
2. **幂等复跑比对时，这四个键必须排除**：`generated_at`、`dates`（含 trade_status 等易变元数据）、
   `indexes`（`float_mv` / `total_mv` 尾数抖动）、`index_hist`（本条窗口滑动）。
   只比 **`D0` / `D1` / `today_zt_quotes` / `yesterday_zt_today`** —— 这四个一致即可判定「数据未变、报告可复用」。
   本次若把 `index_hist` 也纳入比对，会看到 8 行「差异」而误判为数据变化、白跑一遍完整流程。

```python
CORE_KEYS = ("D0", "D1", "today_zt_quotes", "yesterday_zt_today")   # 幂等判定只看这四个
same = all(json.dumps(canon(a[k]), ensure_ascii=False, sort_keys=True)
           == json.dumps(canon(b[k]), ensure_ascii=False, sort_keys=True) for k in CORE_KEYS)
```

### 12. 东财炸板池 `em_ZB` 里含有「盘中打开后回封」的票，不等于「炸板未回封」⚠️

`em_ZB.pool` 记录的是**当日曾经打开过涨停**的标的，其中一部分**收盘仍封回涨停**。
2026-09-22 实测：`em_ZB` 共 18 只，其中 **瑞芯微（603893，流通市值 922 亿）收盘 +10.00%**，
即盘中打开后回封——把它算进「炸板未回封」会凭空多出一个「大票炸板」的利空证据。

**判据**（收盘涨幅是否达到涨停，注意创业板/科创板阈值 20%）：

```python
def is_limit(z):
    thr = 19.8 if (z["c"].startswith("30") or z["c"].startswith("688")) else 9.8
    return (z.get("zdp") or 0) >= thr

zb_open   = [z for z in em_ZB_pool if not is_limit(z)]   # 真·未回封
zb_sealed = [z for z in em_ZB_pool if is_limit(z)]       # 打开后回封
```

**处理规范**：讲「炸板池构成」时须显式区分两类，报告写「N 只炸板股中 M 只回封（××，收盘仍涨停），
其余未回封；未回封阵营里流通市值最大的是……」。**不要**直接按流通市值排序取前几名当「炸板代表」。

### 13. `idx_cmp` 只覆盖 4 个指数，其余指数的「昨日涨跌幅」要另行补全

`zt_analyze.py` 输出的 `S["idx_cmp"]` 只含 **上证指数 / 深证成指 / 创业板指 / 科创50** 四个。
报告要展示「上证50 / 中证1000 / 国证2000 等指数今日 vs 昨日」时，这些键缺失 →
表格会渲染成 `—`（虽不报错，但读者会以为数据缺失）。

**补全方式**：读上一交易日的 `out/zt_review_{D1}.json`，其 `indexes[name].pct`
就是那一天的涨跌幅；`amount_wan` 同理可用于算各指数的成交额环比。

```python
B1 = json.load(open(f"out/zt_review_{D1}.json", encoding="utf-8")) if os.path.exists(...) else None
if B1:
    for v in B1["indexes"].values():
        prev_amt[v["name"]] = (v.get("amount_wan") or 0) / 10000.0
        PREV_IDX_PCT.setdefault(v["name"], v["pct"])   # 不要覆盖 idx_cmp 的权威值
```

这条同时解决了「上证50 成交额环比」这类风格对比指标——分析「增量资金去了权重还是小微盘」
必须用到它，而它并不在 `idx_cmp` 里。

**报告侧可复用件**：与其逐个 P 占位符手工拼「各指数成交额环比」表，不如写一个 `tbl_sty` 生成器——
`amt_yoy(nm)` 取「今日 `ixr[nm].amt` ÷ 上一交易日 `idx_prev_amt[nm]`」，再用 `PREV_IDX_PCT` 补昨日涨跌幅，
一次覆盖 8 个风格指数（科创50 / 上证50 / 沪深300 / 中小100 / 中证500 / 创业板指 / 中证1000 / 国证2000）。
2026-09-23 实测该表直接孵化出当日主论点（权重缩幅 -34% vs 小微盘 -10.9%）。

### 14. `ths_zt` 是分层结构，取涨停名单必须用 `ths_zt["info"]` ⚠️

`zt_fetch.py` 落盘的每个日期节点里，同花顺涨停池的原始响应被放在 `ths_zt`，它是**一个字典**：

```json
{"total": {"today": {...}, "yesterday": {...}},
 "limit_down_count": {"today": {...}, "yesterday": {...}},
 "date": "20260923", "trade_status": {...},
 "info": [ ...每个涨停股的明细... ]}
```

即「涨停家数汇总」在 `ths_zt["total"]`，**「涨停股名单」在 `ths_zt["info"]`**，两者是兄弟键。
（`ths_zb` / `ths_dt` 是同一形状，分别放炸板池 / 跌停池。）

若把名单误写成 `ths_zt["total"]["info"]` → **静默得到空集**（`.get()` 不报错），
于是报告脚本里的北交所差额自检 `set(em_codes) - set(ths_codes)` 会把**全部涨停股**都算成"差额"，
`assert all(c.startswith("92"))` 抛错，报错内容看起来非常像真的字段错位，容易白排查半天。

```python
# 正确
ths_codes = {x["code"] for x in (B["dates"][D0]["ths_zt"] or {}).get("info") or []}
num = ((B["dates"][D0]["ths_zt"] or {}).get("total") or {}).get("today", {}).get("num")
# 错误（静默空集）
ths_codes = {x["code"] for x in (B["dates"][D0]["ths_zt"] or {}).get("total", {}).get("info", [])}
```

排查信号：差额里出现**沪深代码**（而非清一色 `92` 开头）时，先怀疑是不是拿到了空名单，
再去怀疑字段错位。

### 15. 跌停家数两源不一致的第二种形态：`em_DT.tc > 0` 但 `em_DT.pool` 为空

第 9 条讲的是「同花顺跌停池接口 404 → 只能用汇总字段」。2026-09-23 出现**另一种**形态：

| 源 | 值 |
|---|---|
| 同花顺 `limit_down_count.today.num` | 12 |
| 东财 `em_DT.tc` | 13 |
| 同花顺 `ths_dt` | `None`（接口 404） |
| 东财 `em_DT.pool` | `[]`（空，但 `tc`=13） |

即**两源家数差 1 只，且两边的明细都拿不到 → 差额无法归因**（既不能像涨停池那样验证是不是北交所，
也不能忽略不计）。

**处理规范**：
1. 报告一律**采用同花顺汇总口径**（`limit_down_count`），不要自己数池子、也不要用东财 `tc`；
2. 在「数据口径」里**显式写出两源数值与差额**，并说明差额不可归因的原因（明细池为空 / 接口 404）；
3. **不要**因为「东财 pool 为空」就写「东财也是 0 家」——`tc` 与 pool 是独立字段，会自相矛盾。
4. 跌停封死率取 `limit_down_count.today.rate`（= num / (num + open_num)），
   它和封板率一样是判断退潮形态的关键：2026-09-23 跌停 12 家而封死率 75%，
   与「跌停 27 家」的恐慌杀跌是两种不同的退潮。

### 15b. 跌停家数两源不一致的**第三种形态**：池非空，但差额全是沪深代码

2026-10-08 实测：

| 源 | 值 |
|---|---|

### 18. 判读「缩量下跌 + 封板率回升」：用「触及涨停家数」区分参与度与承接力

2026-09-24 的形态：指数全线中阴（-1.2%~-2.7%）、两市成交 -6.3%，但**涨停家数持平（51→51）、炸板腰斩（26→10）、封板率 66.2%→83.6%**。
如果只看封板率会得出「情绪修复」，是错的。正确做法是同时算三个量：

| 量 | 公式 | 含义 |
|---|---|---|
| **参与度** | 触及涨停家数 = `num + open_num`（= `history_num`） | 愿意去冲板的资金量 |
| **承接力** | 封板率 = `num / history_num` | 冲上去能否封住 |
| **破坏力** | 跌停 `num` 与封死率 `rate` | 亏钱效应 |

09-24 实测：参与度 77 → 61（-21%），承接力 66.2% → 83.6%。**两者背离 → 结论是"参与收缩 + 失败率下降"，
不是"资金回流"**，本流程命名为**收缩式锁仓**（另两条佐证：涨停股合计成交 -15%、单只中位成交 -15%，而封单中位数 +13%）。

反例对照：09-23 是参与度 80→77（几乎不动）而承接力 77.5%→66.2%（掉 11.3pct）→ **"承接力退潮"**。
**同样是"封板率变化"，方向相反，结论完全相反——所以这两个量必须一起看。**

### 19. 东财跌停池默认排序会返回空 `pool`，必须显式 `sort=fund%3Aasc` ⚠️

### 22. 当日「触及涨停家数」不能用 `senti[D0]["yest"]["history_num"]` ⚠️

`senti[D0]["yest"]` 存的是 **D0 抓取时接口返回的「前一交易日」统计**（即 D1 的今日值），
不是 D0 自己的触及家数。2026-09-29 出报告时误用，把「今日触及涨停 64 家」渲染成了「44 家（= 9/28 的值）」，
连带 KPI 卡的环比方向也写反。

**正确取值**：当日 / 前一日的「触及涨停、触及跌停、封死率」一律直接从 review 文件取：

```python
d0 = B["dates"][D0]["ths_zt"]; d1 = B["dates"][D1]["ths_zt"]
TOUCH0  = d0["total"]["today"]["history_num"]                  # 今日触及涨停
TOUCH1  = d1["total"]["today"]["history_num"]                  # 昨日触及涨停
DTOUCH0 = d0["limit_down_count"]["today"]["history_num"]       # 今日触及跌停
DSEAL0  = d0["limit_down_count"]["today"]["rate"] * 100        # 今日跌停封死率
```

注意 `limit_down_count` 与 `total` 是 **`ths_zt` 下的平级键**（不是 `total` 的子键），
写成 `d0["total"]["limit_down_count"]` 会 `KeyError`。
**自检**：`触及涨停家数 ≥ 涨停家数`，且 `触及涨停 - 涨停` 应大致等于 `炸板家数`（可差几只，因炸板池口径）。

### 25. 「全线放量 + 全线下跌」的唯一解释是抛压，不是资金回流 ⚠️

### 34. 「封板率上升」可能是**分母收缩**造成的假改善 —— 必须同看封住家数的绝对值 ⚠️（2026-10-15 首次捕获）

10-15 实测：封板率 60.0% → **83.7%（+23.7pct）**、炸板 24 → 7 只，看起来是承接力大幅修复；但同一时间：

| 指标 | 10-14 | 10-15 | 读数 |
|---|---|---|---|
| 涨停家数（分子） | 36 | **36（不变）** | — |
| 触及涨停家数（分母） | 60 | **43（−17）** | 冲板意愿坍缩 |
| 封板率 | 60.0% | 83.7% | 分母掉 28% 的机械结果 |

- **正确写法**：「封板率由 X% 抬到 Y%（+Zpct），但这个改善来自分母收缩 —— 封住的只数没变（36 → 36），少掉的 17 只全是『今天没去冲板』的票」。
- **配套必看项**：① 炸板池回封只数（当日 7 只炸板 **0 只回封**，连续第 3 日零回封）；② 炸板池里从涨停砸到翻绿的极端样本（10-15 掌阅科技收 −3.04%、成交 34.72 亿）。
- 同型陷阱：09-24「封板率回升」是真锁仓（当日触及涨停同步下滑但封住家数也在降）；判别的分界线就是**分子有没有变**。

### 35. 涨停股「吸金密度」跌破 3% 下限有**两种成因**，二次校验方式不同 ⚠️

`涨停股合计成交 ÷ 两市成交额` 的口径自检区间是 3%~8%。跌破下限的两种情形：

| 成因 | 样本 | 特征 | 二次校验 |
|---|---|---|---|
| 家数腰斩 | 09-17（47 家 → 2.0%） | 涨停家数大幅减少 | 单只中位成交额**高于**前日 → 字段无误 |
| 两市放量 + 涨停股成交不变 | **10-15（36 家、1.3%）** | 家数没少，分母放大了 15.5% | 涨停股**合计成交绝对值**与前日几乎一致（214 亿 vs 214 亿）→ 字段无误 |

- **固化动作**：出报告时同时打印 `涨停股合计成交额`、`昨日合计成交额`、`单只中位成交额`、`昨日中位`四个值，
  再写「占比为何低」的说明。**只看占比会把「分母放大」误诊为「数据缺失」**。
- 10-15 同时出现的结构信息：首板占 83%、最大成交股仅 21.15 亿 → 涨停股整体在往小市值/低成交倾斜。

### 36. 「板块性杀跌」的认定流程（跌停池做产业链归并的可复用做法）

跌停家数 > 20 或跌停 ≥ 涨停时，除了按行业聚类，**还必须验证"是不是一个板块在集体杀"**：

1. 对跌停池按 `hybk` 聚类，取最大行业（10-15 = 航运港口 4 只）。
2. **拉该行业的全部主要个股腾讯快照**（自建列表，20 只左右），算：下跌只数 / 跌停只数 / 均值 / 中位。
3. 判定：`跌停只数 ≥ 3` 且 `下跌占比 ≥ 80%` → **板块性杀跌**；否则按分散个股处理。
4. 同时给`跌停池成交额占比`与`该集群合计流通市值`两个强度指标。

10-15 结果：航运港口 4/20 跌停、19/20 下跌、中位 −3.84%、占跌停池成交 **42%**、合计流通 2696 亿 → 板块性成立。
→ **反例对照**：10-14 跌停 11 只散落 11 个行业、每行业 1 只 → 彻底去板块化，不适用本流程。

### 37. 消息面归因必须「事实层 / 事件催化」分离，并显式声明不替市场做方向判断 ⚠️（2026-10-15 首次成文）

当某板块出现异常下杀且确有公开消息时，报告的写法固定为三段：

1. **事实层（数据）**：只写行情数据 —— 跌停只数、成交额、占跌停池比例、全板块下跌只数与中位。**不掺入因果**。
2. **事件催化（媒体转述）**：逐条列消息，**每条都带来源机构 + 日期**，并统一加一句「媒体转述，非本报告一手取证」。
3. **归因说明**：若多条消息对价格的方向指向**相互矛盾**（10-15：制裁放宽 = 运价利空 vs 海峡袭击升级 = 运价利多），
   **必须写出「市场选择了哪一条来定价」，并明确声明本报告不对该类地缘/政策消息做方向判断、不建议据此交易。**
4. 报告末尾「风险提示」里再重复一次该免责（消息为转述、方向有矛盾、请勿据此交易）。

**严禁**把自媒体/AI 生成内容当作事实依据；只用权威媒体（央视新闻、证券时报、中国基金报等）并标注时点。

### 38. 所有**跨日对比**的数字必须从 `zt_stats_{D1}.json` 现算，不能凭记忆写「上一日是多少」 ⚠️（2026-10-15 首次捕获）

10-15 报告初稿在「首板组 vs 连板组中位」一段里手写了一句
「10-14 是『连板组中位 **+9.96%** vs 首板组 **−3.04%**』」—— 回 10-14 报告原文核对，
真实读数是「首板组中位 **−1.70%** / 连板组中位 **−1.93%**」。**+9.96% 这个数在任何一期报告里都不存在。**

根因：跨日对比句里的「上一日数值」是全文**唯一无法从当日数据里自证**的数字，
写的时候最容易凭语感/记忆编一个「看起来合理」的值，且渲染后完全看不出异常。

处置（已固化为脚本代码）：

```python
# 上一交易日（D1 复盘）的分组中位：从 zt_stats_{D1}.json 现算，禁止手写
_py = json.load(open(os.path.join(OUT, "zt_stats_%s.json" % D1), encoding="utf-8"))["perf"]
_gy_s = [p["pct"] for p in _py if (p["lbc"] or 1) == 1 and p["pct"] is not None]
_gy_l = [p["pct"] for p in _py if (p["lbc"] or 1) >= 2 and p["pct"] is not None]
m_s_y, m_l_y = median(_gy_s), median(_gy_l)
assert len(_gy_s) + len(_gy_l) == len(_py), "D1 分组计数不闭合"
P("GAP_S_M_Y", ...); P("GAP_L_M_Y", ...); P("GAP_L_DELTA", ...); P("GAP_S_DELTA", ...)
```

**推广**：凡是「与上一交易日对照」「此前 N 次均为 X」这类句子，
① 数值走占位符 + 从 `zt_stats_{D1}.json` / 历史报告里现算；
② **计数**（连续第 N 个交易日、第 N 次验证）也要与本报告里**列出的日期清单**严格对齐 ——
10-15 初稿写「连续第 6 个交易日（09-29/09-30/10-09/10-12/10-13/10-14/10-15 全部验证）」，
清单是 7 个、数字是 6，自相矛盾。改为「共 7 次交叉验证，结果无一例外都是 0 只」，
用**可枚举的清单**替代**靠累加维护的序数**（序数每期都会漂移）。
**交付前 grep**：`grep -oE '(连续第|共) ?[0-9]+ ?(个交易日|次)' 报告.html`，逐条与清单核对。

**10-19 再次踩到同一坑（形态更隐蔽）**：初稿写「连板组中位强于首板组，差 2.01pct，**与上一交易日的 0.97pct 方向一致**」，
但 `GAP = 首板中位 − 连板中位`，上一交易日 `GAP_Y = +0.97`（正数 = **首板**强），今日 `GAP = −2.01`（负数 = **连板**强）
→ **方向相反**，却因为两个数都被渲染成绝对值/带符号的小数而看不出问题。
**规则**：凡是引用 `GAP*` 系列的句子，必须先把符号翻成人话（正 = 首板强 / 负 = 连板强）再落笔，
并在模板里把方向写成「首板组 X% 略强/弱于连板组 Y%」，**不要只写一个差值**。

### 39. 补抓历史交易日作为 D1 时，`zt_review_{D1}.json` 的 `indexes` 是**抓取当时**的实时快照 ⚠️（2026-10-19 首次捕获）

是**今日**的实时快照（`amount_wan` / `pct` 全是今日值），**不是 D1 当日的值**。
若沿用旧模板的 `amt_yoy()`（读 `zt_review_{D1}.json` 的 `indexes` 算环比），会得到
**10 个指数环比全部 = 0.0%** 且不报错 —— 报告会写成"量能完全持平"，是纯粹的假数据。

正确做法：**D1 的成交额与涨跌幅一律从指数日线按显式日期取**（与 `index_hist` 同一思路），
落成 `out/_idx_amt_{D1}.json` 后再进模板：

```python
MAP = {'上证指数':'zs_1A0001','深证成指':'zs_399001','创业板指':'zs_399006','科创50':'zs_1B0688',
       '沪深300':'zs_1B0300','上证50':'zs_1B0016','中证1000':'zs_1B0852','中证500':'zs_1B0905',

# 按行内日期字符串取 D1 与 D1-1 两行，环比 = amt(D1)/amt(D1-1)-1
```

### 40. 概念板块榜的 `high` 字段是「板块内个股**累计**涨停记录」，不是最高连板 ⚠️（2026-10-19 首次成文）

### 41. 三日序列表的「前日」跌停统计要取 **D1 文件**的 `yesterday`，不是 D0 文件的 ⚠️（2026-10-23 踩到）

## 报告生成类

- **不要用 f-string 生成含 CSS/JS 的 HTML**：`{` `}` 转义是地狱，`data:{json.dumps(x)}` 需写成
  `{json.dumps(x)}}}`（3 个右花括号）且极易漏。统一用 `__占位符__` + `str.replace`。
- 收尾必查占位符残留：`re.findall(r"__[A-Z_0-9]+__", html)` 必须为空。
- ECharts 横向条形图**类目 >25 时**容器高 ≈ 类目数 × 21px 且 `axisLabel.interval: 0`，
  否则标签跳显、与柱子视觉错位。**`interval: 0` 必须写在 `axisLabel` 对象里**：把 `yAxis` 传成
  纯数组（`yAxis: [{type:'category', data:[...]}]` 里 `axisLabel` 写成标量）时会被 ECharts 按默认抽稀，
  2026-09-28 的 `c_perf`（51 只昨日涨停股）就只显示了约一半标签。正解：
  ```js
  yAxis: { type:'category', data: names, axisLabel:{ fontSize:9, interval:0 }, splitLine:{ show:false } }
  ```
  并把容器高从 700px 提到 900px（51 × 21 ≈ 1071，可留白）。
- 双 Y 轴图图例用 `top:3, left:'center'`，**不要 `right:8`**（会与右侧轴名重叠，渲染成「胜率%率」）。
- 瀑布图不能用 `data:[[起, 止]]`，须「透明占位 stack + 数值 stack」。
- **ECharts 用本地托管而非纯 CDN**（2026-09-20 踩坑）：jsdelivr 在 Playwright 侧会间歇性
  `ERR_CONNECTION_RESET`，表现为自检输出「7 个图表容器 `canvas=0`」+ `PAGEERROR: echarts is not defined`，
  而**同一时刻 `curl` 却能正常下载**——极具误导性，容易去改图表配置。
  正解：`<script src="../assets/echarts.min.js">`（已入库）＋ `if(typeof echarts==='undefined')` 时 `document.write` 回退 CDN。
  另：`cdn.bootcdn.net` / `cdn.staticfile.org` 的 `echarts/5.5.1` 路径实测 404，`lib.baomitu.com` 返回的是错误页，都不可用。
- **ECharts 类目轴首项在底部**：排名类热力图 / 条形图的数组**必须先反转**再传给 `yAxis.data`，
  否则「合计最大」的行业渲染在最下方。热力图 data 是 `[x下标, y下标, 值]`（x=日期、y=行业），别把两个下标写反。
- **「三列对比表」的增量列会渲染出双符号 `++20`** ⚠️（2026-10-08 发现，模板里潜伏自 09-28）：
  模板里的增量列写作 `"{5}{6}".format("+" if delta>=0 else "", "{:+d}".format(delta))`，
  浮点分支用 `"{:.1f}"`（无符号，靠前缀 `+`）**是对的**，但整型分支用 `"{:+d}"`（自带符号）→ 负号正常、
  正数变成 `++20`。正解：整型分支改用 `"{:d}"`，符号统一交给前缀。
  自检：生成后 `grep -o '++[0-9]'` 必须为空。
- **行业迁移表的排序不能只按家数**：`key=-(hy0*2+hy1)` 会把「3→0 的归零行业」排到「1→1 的持平行业」之后，
  于是最该被看见的撤离方向（如 10-08 医疗服务 3→0、生物制品 3→0）被挤出前 18 行。
  正解：把变化幅度纳入权重 —— `key=-( (hy0+hy1) + abs(hy0-hy1)*2 )`，再按 max 与名称 tie-break。
  **标题里写到的行业，正文表格里必须真的出现**（写完对照一次）。
- **`_check_js.py` 依赖 `node` 在 PATH**：managed 环境里 `node` 常在 PATH 里找不到，
  脚本会抛 `FileNotFoundError: [WinError 2] 系统找不到指定的文件`（**不是报告 JS 有问题**）。
  处置：手动提取内联 JS 落盘，用绝对路径跑 `C:/Users/Administrator/.workbuddy/binaries/node/versions/22.22.2-6/node.exe --check <file>`。
  判定标准不变：`rc=0` 即通过。
- **占位符本身已带符号时，正文里不要再补 `+`**（2026-10-09 踩到）：模板写 `成交 +__KC_YOY__%`，
  而 `__KC_YOY__` 渲染成 `+11.6` → 页面出现 `++11.6%`。凡是 `*_PCT` / `*_YOY` / `*_D` 这类
  `"{:+.1f}"` 格式的占位符，正文里**直接写** `__X__%` 即可。
  自检：生成后 `grep -o '++[0-9]'` 必须为空（与「三列对比表整型双符号」是同一条自检）。
- **ECharts 排名条形图的类目顺序**：类目轴**首项在底部**（默认 `inverse:false`），
  所以要让"家数最多的类目显示在最上方"，传进去的数组必须是**升序**（`yAxis.data[0]` = 最小值 → 落在底部）。
  写法：`rows = sorted(items, key=lambda x: x["n"])`（升序）→ 直接 `json.dumps`，**不要 `[::-1]`**；
  若来源已是降序，再 `[::-1]` 反而会把最大项压到底部（10-09 `c_conc` 首版即如此）。
  自检：截图确认第一名在第一行。
- **模板里 `__HY_XX__` 是「昨日」、`__HY_XX0__` 才是「今日」** ⚠️（2026-10-12 踩到）：
  报告脚本里 `hy0` = 今日、`hy1` = 昨日，但占位符命名沿用了旧版习惯 ——
  `P("HY_CB", hy1.get("出版",0))`（=昨日）、`P("HY_CB0", hy0.get("出版",0))`（=今日）。
  于是**凡是写「A→B」的行业对比句都极易写反**：10-12 首版把流入端写成 `__HY_DW0__ → __HY_DW__`，
  渲染出来是「电网设备 4 → 1」（今日→昨日），方向完全颠倒。
  处置：改完这类文案后**必须 grep 渲染结果逐条核对**（`grep -o '电网设备 [0-9]* → [0-9]*' 报告.html`），
  或直接把占位符改名成 `_Y / _T` 后缀以免混淆。
- **`node --check` 不支持 bash 进程替换** ⚠️（2026-10-12 踩到）：`node --check <(python -c ...)` 会报
  `Error: Cannot find module 'D:\proc\<pid>\fd\<n>'`（Windows 上 `/dev/fd` 不存在）。
  必须先 `open('out/_tmp_check.js','w',encoding='utf-8').write(js)` 落盘，再 `node --check out/_tmp_check.js`。
